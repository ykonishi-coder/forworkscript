# ATS（採用管理システム）連携 調査フレームワーク

デフォルトは手動コピペ でセキュリティ重視。ATS との自動連携は、実行時にネット調査で最新方式を確認 してから提案する。

## 大原則（個人情報保護最優先）

1. 連携なし（手動コピペ）を強く推奨: 個人情報の扱いは最小限が鉄則
2. 自動連携が必要な場合のみ検討: 業務効率が必要な大量採用など
3. 毎回その場で調査: MCP / API の最新情報
4. 書き込み権限は最小限: 読み取り only で済ませる
5. 認証情報をスキルに保存しない

## なぜ手動コピペ推奨か

### セキュリティ上の利点

- 送信する情報をあなたが選べる: マスキングも確認できる
- 意図せぬデータ流出がない: 自動連携は大量のデータを一度に動かすリスク
- 監査しやすい: 誰が何を処理したか分かる

### 業務効率との比較

- 1日 5名以下: 手動コピペで全く問題なし
- 1日 10-20名: 手動でも可能、マスキング補助ツールがあると便利
- 1日 30名以上: 自動連携を検討する価値あり

ほとんどの採用担当者は手動コピペで足ります。

## CSV 方式（中間的な推奨）

手動と自動の中間。比較的安全:

1. ATS から毎週の新着候補者を CSV エクスポート
2. CSV をスキルが読み取り
3. 読み取りのみ（ATS への書き込みなし）
4. 評価結果は別途 ATS に手動で反映

### 手順

```
1. ATS から CSV ダウンロード
2. 候補者情報を `./.hiring-assistant/incoming/candidates.csv` に配置
3. スキルに「新着候補者の書類選考して」と依頼
4. スキルが CSV を読んで各候補者を処理
5. 評価サマリを ATS に手動で反映
```

CSV は処理後に削除（自動または手動）。

## API 方式のリスク（参考）

ATS の API 連携は便利だが、リスク大:

### 典型的なリスク

- 意図せぬ大量ダウンロード: API 経由で全候補者情報が Claude に送られる
- 書き込み事故: 評価を勝手に ATS に書き込む → 後から修正困難
- 認証情報漏洩: API Key が git にコミットされる事故
- 削除の不完全: Claude 側で削除しても ATS 側に残る

### 必要な対策

- 読み取り専用トークン
- API Key を OSキーチェーン で管理（`config.yaml` に書かない）
- 処理前に必ずユーザー承認
- 書き込みは ユーザー承認後のみ、プレビュー付き

## スキル側の安全装置

設定 `safety.api_safety` で有効:

```yaml
safety:
  api_safety:
    # API 連携時の暴走防止
    max_candidates_per_session: 10  # 1セッションで最大10名まで
    require_user_confirm_before_fetch: true  # 取得前にユーザー確認
    auto_purge_after_process: true  # 処理後自動破棄
    never_auto_write_to_ats: true  # 自動書き込み禁止
```

## トラブル対応

### 認証エラー
- OAuth 再認証
- API Key の期限確認
- 絶対にやらないこと: 認証情報をスキル設定ファイルに書く

### 大量データの誤取得
- 即座に処理中断
- 取得済みデータを破棄
- ログで影響範囲確認
- 応募者への説明（必要なら）

### 書き込み事故
- ATS 側で該当データを確認
- 不適切な書き込みがあれば削除
- プロセス見直し

## まとめ

- 手動コピペが最も安全でおすすめ
- 自動連携は 業務上必要 なときだけ検討
- MCP / API は 都度最新調査
- 書き込み権限は 最小限
- 認証情報は スキル外で管理
- 暴走防止の安全装置を設定

ATS の連携より、プライバシーを優先 する文化がこのスキルの基本姿勢です。
