# 機能: 候補者比較

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.hiring-assistant/config.yaml` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` はその値を指す。


複数候補者を、評価基準で横並び比較する。

## 大原則

1. 評価基準ベース（属性ではなく能力で比較）
2. 公平性確保: 同じ情報量・同じ基準
3. バイアス検出: advocate が自動チェック
4. 絶対評価と相対評価: どちらも提示
5. 決定はユーザー: 比較材料の提供まで

## 入力

1. 比較対象候補者（2名以上）
2. 評価基準（求人票 or 事前設定）
3. 比較目的（次フェーズ選定 / オファー判断 / 採用決定）

## 手順

### 1. 対象確認

```markdown
比較する候補者を確認します:

1. {候補者A} - 一次面接完了
2. {候補者B} - 一次面接完了
3. {候補者C} - 二次面接完了

比較の目的は？
- 一次面接後の次フェーズ選定
- 最終判断
- オファー条件検討
```

### 2. 各候補者のデータ集約

`screening/` と `interviews/feedback/` から各候補者の評価を読み込む:

- 書類選考結果
- 面接FB（複数面接官分があれば統合済みのもの）
- 技術課題の結果（あれば）

### 3. 評価基準別の横並び比較

```markdown
# 候補者比較

比較日: YYYY-MM-DD
ポジション: シニアエンジニア
対象: 3名

---

## 比較表

| 評価基準 | 候補者A | 候補者B | 候補者C |
|---------|---------|---------|---------|
| 技術スキル（Python） | 🟢 高 (5年) | 🟡 標準 (3年) | 🟢 高 (6年) |
| AWS経験 | 🟡 部分的 | 🟢 高 | 🔴 未経験 |
| 問題解決力 | 🟢 高 | 🟢 高 | 🟡 標準 |
| コミュニケーション | 🟢 高 | 🟡 標準 | 🟢 高 |
| カルチャーフィット | 🟢 高 | 🟢 高 | 🟡 標準 |
| マネジメント経験 | ✅ 3名リード | ❌ なし | ✅ 10名 |
| 成長可能性 | 🟢 高 | 🟢 高 | 🟡 標準 |

### 総合スコア（各5点）

| | A | B | C |
|--|--|--|--|
| 技術 | 4 | 3 | 5 |
| ソフト | 5 | 4 | 4 |
| 総合 | 4.5 | 3.5 | 4.5 |
```

### 4. 候補者別の詳細サマリ

```markdown
## 候補者A

### 強み（他候補比）
- バランス型、どの観点も標準以上
- マネジメント経験が適切な規模

### 懸念
- AWS の深い経験不足（入社後の習得は可能）

### 他候補との違い
- C より幅広い経験、B より技術深さ
- 中途半端ではなく、全方位で標準以上

### 推奨シナリオ
- リーダー候補として最適
- 即戦力として配属可能

---

## 候補者B

### 強み
- AWS の深い経験（C より圧倒的）
- クラウド案件のキーパーソンになれる

### 懸念
- Python の年数が他の2名より短い
- マネジメント経験なし

### 他候補との違い
- クラウド特化なら B
- ただし、マネジメントが必要なら A, C

### 推奨シナリオ
- クラウドインフラ専門職として

---

## 候補者C

### 強み
- 最も深い技術経験（Python 6年）
- 大規模チームのリード経験

### 懸念
- AWS 未経験（重要な歓迎要件を満たさない）
- カルチャーフィット: 自律性への適応に時間かかる可能性

### 他候補との違い
- 技術深さと大規模マネジメント両立
- ただしクラウド要件では弱い

### 推奨シナリオ
- AWS 以外のプロジェクトなら有力
```

### 5. 相対的な推奨

```markdown
## 相対的な推奨

### もしポジションが「リーダー候補」なら
推奨順: A > C > B
- A: バランス、適切なマネジメント規模
- C: 大規模経験だが、AWS 不足
- B: マネジメント未経験

### もし「AWSクラウド特化」なら
推奨順: B > A > C
- B: 明確な強み
- A: 基礎あり
- C: 未経験

### もし「技術深さ重視」なら
推奨順: C, A > B
- C, A: 十分な経験
- B: Python 年数短い

### 総合的には
推奨順: A > C > B（要件に柔軟性ある場合）

ただし、ポジションの具体的な要件 によって順序が変わります。どれを重視しますか？
```

### 6. 意思決定支援

```markdown
## 意思決定のヒント

### 優先判断ポイント
次の決定には、以下の明確化が必要です:

1. AWS要件の硬さ: 必須 or 歓迎？
2. マネジメント期待: 即戦力 or 育成？
3. 即戦力 vs 伸び代: どちらを重視？

### 候補者別シナリオ

#### A を選ぶ場合
- バランス重視
- 入社後に AWS を学ぶ覚悟
- マネジメント実績を活かす配属

#### B を選ぶ場合
- AWS 案件の明確なニーズ
- マネジメントは他者に任せる
- Python は伸び代として期待

#### C を選ぶ場合
- AWS以外のプロジェクト（または社内で AWS 学習サポート）
- 大規模マネジメントの即戦力
- カルチャーへの適応サポート

### AI推奨
A がバランス最良（総合）
ただし、要件次第で B・C も有力
```

### 7. バイアスチェック

`hiring-assistant-advocate` に比較結果を渡してチェック:

```markdown
### バイアスレビュー

#### 🔴 Critical
（なければ空）

#### 🟡 Warning
- 「候補者C はカルチャーフィット 🟡」の根拠が弱い
  - 具体的な面接でのやり取り・発言を確認
  - 「自律性への適応に時間かかる可能性」の根拠は？

#### 🟢 Info
- 比較基準は明確で公平
- 属性（年齢・性別・国籍）への言及なし
```

### 8. 保存

```
{保存先}/comparisons/{候補者ID群}-{YYYY-MM-DD}.md
```

### 9. 次ステップ

```markdown
## 次のアクション

この比較結果を受けて:
- 1人に絞る: オファー判断サポート → 「オファー判断」
- 追加情報が必要: 追加面接 → 「次面接の質問作って」
- 採用決定会議の資料: この比較をチーム共有（※要応募者同意確認）

最終決定は、採用責任者・採用委員会が行ってください。
```

## やってはいけないこと

- 候補者属性で優劣を決める（年齢・性別等）
- 主観的好みで推奨（「A さんが好みだから」）
- 評価基準を候補者によって変える（公平性違反）
- 情報量が違うのに比較する（面接回数が異なる等）
- 採用決定を代行する（判断材料の提供まで）

## 情報量が揃わない場合

候補者ごとに面接段階が異なる場合:

```markdown
## ⚠️ 注意

各候補者の情報量が揃っていません:
- 候補者A: 一次面接完了 → 評価情報充実
- 候補者B: 書類選考のみ → 面接情報なし
- 候補者C: 二次面接完了 → 詳細情報あり

同じ土俵で比較できる部分とできない部分があります。
最終判断前に、情報を揃えることをおすすめします。
```

比較そのものは実行するが、情報量の差 を明示。

## 「似た候補者」の検出

すべての候補者が似た能力・経験を持つ場合:

```markdown
## 候補者がよく似ています

この3名、評価基準上の違いが小さいです:
- 技術スキル: ほぼ同じ
- 経験年数: 4-5年で大差なし
- 面接評価: ほぼ同じ

違いを明確にするには:
- より深い技術課題
- リファレンスチェック
- 実務シミュレーション
- 最終面接でカルチャー適合を深く

現時点の情報では明確な優劣をつけにくいです。
```

主観で無理やり順位づけない。
