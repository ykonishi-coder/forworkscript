# 機能: 要件定義

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.engineer-assistant/config.yaml` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` はその値を指す。


ソフトウェア要件の整理支援。

## 手順

### 1. ヒアリング

- プロジェクト概要
- 解決したい課題
- ユーザー像
- 期待される成果
- 制約（予算・期間・技術）

### 2. 機能要件の整理

#### ユーザーストーリー形式
```
{ユーザータイプ} として、
{目的} のため、
{機能} がしたい
```

例:
```
営業担当として、
顧客情報を素早く把握するため、
顧客詳細画面で過去の取引履歴を一覧表示したい
```

#### 受け入れ基準
```
Given: {前提}
When: {操作}
Then: {結果}
```

### 3. 非機能要件

- パフォーマンス: レスポンス時間、同時接続数
- セキュリティ: 認証・暗号化
- 可用性: SLA、冗長化
- 保守性: ログ・監視
- スケーラビリティ: 将来の成長
- アクセシビリティ: WCAG 準拠
- 国際化: 多言語対応

### 4. 優先順位

MoSCoW 法:
- Must: 必須
- Should: あった方がいい
- Could: できれば
- Won't: 今回はやらない

### 5. 成果物

`templates/requirements.template.md` 参照。

## アウトプット例

```markdown
# 要件定義書

## 1. プロジェクト概要
- 目的: ...
- ゴール: ...

## 2. ユーザーストーリー

### 優先度: Must
- [US-001] 営業担当として、顧客情報を素早く把握するため、顧客詳細画面で過去の取引履歴を一覧表示したい
  - 受け入れ基準:
    - Given: ログイン済み
    - When: 顧客詳細画面を開く
    - Then: 過去1年の取引履歴が表示される

### 優先度: Should
- ...

## 3. 非機能要件
- レスポンス: 2秒以内
- 同時接続: 100人
- セキュリティ: OAuth 2.0

## 4. 技術制約
- バックエンド: {既存スタック}
- フロントエンド: ...
```

## やってはいけないこと

- 実装方法の先取り（要件に実装を混ぜない）
- 曖昧な表現（「使いやすく」等）
- テスト不能な要件（具体的な基準を）
