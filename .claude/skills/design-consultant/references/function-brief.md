# 機能: デザインブリーフ整理

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.design-consultant/config.yaml` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` はその値を指す。


デザインの要件を構造化する。

## 目的

デザイン制作の前に、「何のための」「誰向けの」「どんな」デザインを作るかを明確にする。

## ヒアリング項目

### 1. プロジェクト基本情報
- プロジェクト名
- 依頼主
- 納期
- 予算感（任意）

### 2. 用途
- Web / ロゴ / バナー / 資料 / 印刷物 / アプリ / パッケージ

### 3. 目的
- 何を達成したい？（申込数増 / ブランド認知 / 情報伝達 / 好感度 等）
- KPI（ある場合）

### 4. ターゲット
- 年齢・性別・職業
- 生活スタイル
- 情報リテラシー
- ペルソナ（できれば）

### 5. トーン＆マナー
- 堅実 / モダン / 親しみ / エッジ 等
- 好きな参考例
- 嫌いな方向性（NG）

### 6. ブランド情報
- ロゴ（ある/ない）
- ブランドカラー
- 指定フォント
- ブランドガイドライン

### 7. 競合・参考
- 競合のデザイン
- 参考にしたい既存事例
- 差別化ポイント

### 8. 制約
- 必須要素（ロゴ必須 / 特定メッセージ必須）
- 禁則（使ってはいけない色 / 表現）
- 技術的制約（印刷 CMYK / Web RGB / 画面サイズ）

## 整理後のブリーフ

`templates/design-brief.template.md` の形式で保存:

```
{保存先}/briefs/{案件名}-{日付}.md
```

このブリーフが、以降の全工程（コンセプト・配色・レイアウト）の基盤になる。

## ブリーフ品質チェック

- [ ] 目的が1文で言えるか
- [ ] ターゲットが具体的か（漠然としていないか）
- [ ] トーン＆マナーに具体性があるか
- [ ] 成功基準が定義されているか
- [ ] 制約が明確か

抜けがあれば、ユーザーに追加ヒアリング。
