# 機能: LP（ランディングページ）の HTML/CSS 生成

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.design-consultant/config.yaml` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` はその値を指す。


商品・サービス・イベントを紹介する1枚の縦長ページ（LP = ランディングページ）を、HTML/CSSで生成する機能。

## LPって何？（初心者向け）

- LP = Landing Page（ランディングページ）の略
- ユーザーが広告やSNSから「着地（ランディング）」する専用ページ
- 通常のWebサイトと違い、1つの目的（商品購入・問い合わせ・登録）に絞って作る
- 縦長で、上から順に読むと自然に行動したくなる構造

LPの目的をシンプルに言うと、「読んだ人に、1つの行動を取ってもらうこと」。

---

## 入力として受け取るもの（ヒアリング）

ゼロからLPを作る場合、最低限ヒアリングしたい項目:

1. 何のLPか（商品/サービス/イベント/採用/他）
2. 誰向けか（ターゲット像 = ペルソナ）
3. このLPのゴール（購入/申込/問い合わせ/登録/資料請求 など）
4. 主な訴求点（強み・ベネフィット・差別化）
5. 必須に載せる要素（実績数値・お客様の声・FAQ・価格 など）
6. トーン（フォーマル / フレンドリー / 高級感 / 親しみ / 等）
7. ブランド（既存ロゴ・色・フォント）
8. 想定の閲覧環境（スマホ中心 / PC中心 / 両方）
9. 公開先（独自ドメイン / Vercel のサブドメイン）
10. 参考にしたい既存LP（3本程度）

不明点は1〜2往復でまとめて聞く。

## 標準構成（典型的なLP骨格）

```
1. ヒーロー（ファーストビュー）
   - キャッチコピー
   - サブコピー
   - 主要CTA（行動喚起ボタン）
   - 主要ビジュアル

2. 問題提起・共感
   - 「こんなお困りありませんか？」

3. 解決策・サービス紹介
   - ベネフィット 3〜6個

4. 特徴・機能
   - スクショ・図解

5. 実績・お客様の声
   - 数字・事例

6. 価格（必要なら）

7. FAQ

8. 会社概要・運営情報

9. 最終CTA
   - 繰り返しの行動喚起
```

業種・目的によって構成は増減。最初にユーザーと骨格を合意してから実装に入る。

## 生成ワークフロー

### ステップ1: ワイヤーフレーム
- 文字だけで全セクションの構成・各セクションの要素・コピー案を並べる
- ユーザーと合意してから実装に進む

### ステップ2: デザイン方針
- 配色（palette モードと連携）
- フォント（typography モードと連携）
- 雰囲気の参照URL（ムードボードから）

### ステップ3: HTML 骨組み生成
- セマンティックHTML（header / main / section / footer）
- アクセシビリティ配慮（alt 属性、見出しレベル、コントラスト）
- 構造化データ（必要なら）

### ステップ4: CSS 実装
- モバイルファースト
- Flexbox / Grid で組む
- `rem` / `%` / `clamp()` で可変
- カラーは CSS 変数化
- 外部フォントは `@font-face` か Google Fonts の link
- 必要ならプレーンCSSとTailwind CSSの2案を出す

### ステップ5: 画像プレースホルダー
- 本物の画像は後差し替え
- プレースホルダーは画像生成プロンプト（image-prompt-generator 連携）とセットで提案
- OGP画像は banner モードで別途生成

### ステップ6: コピーとリンク
- コピーは content-creator と連携する場合あり
- 送信先（フォーム宛メール / Google Forms / Typeform 等）を確認
- 利用規約・プライバシーポリシーへのリンクを確認

### ステップ7: レビュー
- advocate に渡して、デザイン原則・アクセシビリティ・景表法をチェック
- 「効果◯◯倍！」など誇大表現を含まないか必ず確認

### ステップ8: 公開
- vercel-deploy モードへ引継ぎ
- プレビュー → ユーザー承認 → 本番昇格

## ファイル構成の推奨

```
{project-name}/
├── index.html
├── styles.css
├── script.js          （必要なら）
├── assets/
│   ├── images/
│   ├── fonts/         （ローカルフォント使用時）
│   └── favicon.ico
├── README.md
├── .gitignore
└── vercel.json        （Vercel設定必要なら）
```

静的サイトとして公開できる最小構成。ビルドツール（Vite / Next.js 等）が必要かはユーザーと相談。

## デザイン品質チェックリスト

- [ ] モバイル幅（320px〜）で崩れない
- [ ] 見出しレベルが順番通り（h1 → h2 → h3）
- [ ] 画像に alt 属性
- [ ] リンクの目的が明確（「こちら」「クリック」だけにしない）
- [ ] コントラスト比 WCAG AA（通常文字 4.5:1 以上）
- [ ] フォントサイズ 16px 以上を基本
- [ ] CTAボタンは指でタップしやすい（44x44px以上）
- [ ] 読み込み速度（画像圧縮、不要CSS排除）
- [ ] `<title>` / `<meta description>` / OGP タグ
- [ ] faviconを用意
- [ ] フォーム送信の成功/失敗メッセージ

## 景表法・表示規制への配慮

- 「効果◯◯倍」「必ず」「絶対」など誇大表現を避ける
- 根拠のない「NO.1」「業界最高」などは使わない
- 医療・健康・金融は特別な規制があるため、使う表現は必ず規約と照合
- 利用者の声は実在・同意を得たもののみ
- 広告表記（「PR」「広告」）が必要な業界は忘れずに

advocate が景表法・薬機法・金商法の観点でも必ずレビュー。

## 他エージェントとの連携

- content-creator: キャッチコピー・本文コピーの作成依頼
- image-prompt-generator: メインビジュアル・セクション画像の生成プロンプト
- engineer-assistant: フォーム送信バックエンド・アナリティクス実装
- marketing-strategist: ターゲット・訴求の検証
- customer-support-advisor: FAQ 内容の検証
- legal-advisor: 特商法・プラポリ・利用規約のドラフト

連携は必ずユーザー承認を取る。

## 絶対にやらないこと

- 景表法・薬機法違反の表現を含めたまま生成
- 他社LPの無断コピー（構成参考は可、デザイン・コピー丸写し不可）
- 認証情報・フォームのAPIキーを HTML / JS に平文埋め込み
- 「完成しました」と言い切る（必ずプレビュー → 承認 → 本番の流れ）
- バックエンドを勝手に作る（engineer-assistant 領域、明示依頼があれば連携）
