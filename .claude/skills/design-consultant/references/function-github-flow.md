# 機能: GitHub PR ベース運用

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.design-consultant/config.yaml` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` はその値を指す。


サイト・LPの変更を、GitHub の PR（プルリクエスト）経由でレビュー・マージする運用フロー。

## PRって何？（初心者向け）

- PR = Pull Request の略
- 「こういう変更を加えたいので、取り込んでください」という提案を、レビュー可能な形で投げる仕組み
- 本番を直接書き換えるのではなく、別ブランチで作業 → 差分を見せる → 承認 → 取り込み、という流れ

直接本番を書き換える運用は事故が起きやすい。一度立ち止まってレビューする仕組みが PR です。

---

## 使う前提

- GitHub アカウント
- `git` コマンド または GitHub CLI (`gh`) が使える状態
- 対象リポジトリへの push 権限
- リポジトリの運用ルール（ブランチ命名・PR テンプレ等）がある場合はそれに従う

---

## 基本フロー

```
1. 最新の main を取得
   git switch main
   git pull

2. 作業ブランチを切る
   git switch -c fix/hero-copy

3. 修正作業
   （site-update / lp-build モードで実施）

4. ローカル確認
   （npm run dev / ブラウザで見る）

5. コミット
   git add ...
   git commit -m "変更の目的を日本語で"

6. プッシュ
   git push -u origin fix/hero-copy

7. PR 作成
   gh pr create --title "..." --body "..."

8. プレビュー確認
   （Vercel の自動プレビュー URL）

9. レビュー・修正
   必要なら commit を追加

10. マージ
    gh pr merge --squash
    （ユーザー承認後）

11. デプロイ確認
    本番で最終確認
```

---

## ブランチ命名の推奨

| 目的 | 接頭辞 | 例 |
|------|-------|-----|
| 機能追加 | feat/ | `feat/add-faq-section` |
| 修正 | fix/ | `fix/broken-og-image` |
| リファクタリング | refactor/ | `refactor/lp-structure` |
| ドキュメント | docs/ | `docs/update-readme` |
| デザイン調整 | chore/ | `chore/update-palette` |

チームに命名ルールがあればそちらを優先。無ければ上記を採用。

---

## コミットメッセージの推奨

- 日本語で簡潔に
- 1行目 50〜70 文字程度
- 「何を・なぜ」を書く（「どう変えたか」は差分を見ればわかる）

例:
```
LP のヒーローコピーを改定
価格セクションに特商法リンクを追加
OGP 画像サイズを 1200x630 に修正
```

---

## PR 本文の推奨フォーマット

```markdown
## 変更の目的
（なぜこの変更が必要か）

## 変更内容
- 変更1
- 変更2
- 変更3

## 確認ポイント
- [ ] プレビュー環境で表示確認
- [ ] スマホ・PC 両方で崩れないか
- [ ] OGP画像の反映確認（必要なら）
- [ ] 景表法・薬機法表記の再チェック

## スクリーンショット
Before / After を添付

## 関連Issue / 参考
（あれば）

## デプロイ後の確認
- [ ] 本番 URL で最終確認
- [ ] GA / 計測タグが動く
```

`templates/pr-description.template.md` に雛形あり。

## レビュー観点リスト

- [ ] コード自体の妥当性（HTML/CSS が正しい）
- [ ] アクセシビリティ（alt・コントラスト・キーボード操作）
- [ ] レスポンシブ（3ブレイクポイント以上）
- [ ] 景表法・薬機法・特商法の観点で表現問題なし
- [ ] 著作権・肖像権（画像・フォントの商用可否）
- [ ] SEO（title / description / OGP）
- [ ] パフォーマンス（画像サイズ・不要CSS）
- [ ] セキュリティ（APIキー漏洩・外部スクリプトの信頼性）
- [ ] ブランドガイドラインの遵守

複数人レビューが理想。1人運用でも、自分で「一晩おいて再度レビュー」が効く。

---

## CI（自動チェック）の推奨

プロジェクト規模に応じて:

- HTMLLint / Prettier / ESLint
- Lighthouse CI（パフォーマンス・アクセシビリティ）
- Vercel 自動プレビュー（PR ごと）
- 壊れリンクチェック

最小構成でも Prettier と Vercel プレビューだけ入れておくと事故が減る。

---

## マージ戦略

- Squash: PR の全コミットを1つにまとめる（推奨・履歴がきれい）
- Merge commit: 履歴を残す（複雑な機能追加時）
- Rebase: 直列履歴（上級者）

静的サイトなら Squash がシンプルでおすすめ。

---

## 禁止事項

- main / master に直接 push
- `git push --force` を独断で実行（上流を書き換える破壊的操作）
- レビュー無しでマージ（1人運用でも最低1日おいて読み直す）
- 本番デプロイ時にプレビュー確認をスキップ
- PR に認証情報・APIキー・個人情報を書く

## 他エージェント連携

- engineer-assistant: コードレビュー観点の強化
- security-guard: PR 内容の監査・CLAUDE.md や hooks 更新時のゼロトラスト点検
- text-quality-checker: PR 本文の誤字脱字チェック

連携は必ずユーザー承認を取る。
