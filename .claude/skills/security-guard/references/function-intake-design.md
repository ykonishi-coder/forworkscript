# 機能: 入口設計（Intake Design）

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.security-guard/config.yaml` と
> `./.security-guard/zero-trust-profile.md` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` は config.yaml の値を指す。
> zero-trust-profile.md が既に存在する場合は、その「現状棚卸し」「リスク評価」「intake_ready」を
> 出発点として、ユーザーには差分（前回からの変化・新規追加）だけをヒアリングする。
> 毎回ゼロから棚卸ししない。プロファイルが無い場合のみ、本ファイルのフルワークフローを実行する。


「何を渡すか」を徹底的に分離する設計サポート。

## なぜ入口設計が必要か（初心者への説明）

強いパスワード・MFA・暗号化といった 「漏らさない対策」は当然やります。
でも現実には以下が起きます:

- 攻撃手法が進化して 昨日安全だったものが今日破られる
- 自分じゃなく 信頼していたサービス側が侵害される（サプライチェーン攻撃）
- 人間のミスは完全にはゼロにできない（1クリックのフィッシング）

だからこそ、万一漏れても被害が限定される構造を、あらかじめ作っておく ことが、現代セキュリティ（ゼロトラスト）の最前線の実装です。

具体的には 「このキー／カード／口座が漏れたら、被害はいくらまで」を事前に決めておく。
これによって、問題が起きた時に「全生活が破綻」ではなく「その専用カード停止で済む」状態を作れます。

## 対象領域

### 1. 銀行口座の分離

#### 提案する構成

```
メイン口座（給与受取・大きな支払い）
  └─ 絶対にAI・SaaSに渡さない
  └─ 明細にAI料金が混ざらない

AI・サービス用 サブ口座（小〜中額 / 月次チャージ）
  └─ AI API料金 / SaaSサブスク / 自動引き落とし
  └─ 残高は月額の2〜3倍程度をキープ
  └─ 漏れたら最悪その残高分の被害

実験用 プリペイド / 少額口座
  └─ 新サービスお試し・検証
  └─ 使い捨て感覚でチャージ
```

#### 具体的選択肢（都度 WebSearch で最新確認）

- 日本の場合:
  - 住信SBIネット銀行の目的別口座
  - 楽天銀行の複数口座
  - GMOあおぞらネット銀行
  - みんなの銀行（デジタル専業）
  - Kyash / B/43（ウォレット型）

- 海外・多通貨の場合:
  - Wise（旧 TransferWise）
  - Revolut

必ず最新情報を WebSearch で確認 してから提案する（手数料・上限・規約は頻繁に変わる）。

---

### 2. クレジットカード・決済の分離

#### 提案する構成

```
メインカード
  └─ AI / SaaS には登録しない
  └─ 生活・出張・大きな買い物用

AI・SaaS 用カード（上限設定 or 少額デビット）
  └─ Claude / OpenAI / Cursor / Replit 等
  └─ 月額上限 1〜5万円程度
  └─ 漏れてもカード停止で済む

実験・単発用 バーチャルカード
  └─ 新サービス登録
  └─ 都度発行・即破棄
```

#### 具体的選択肢（都度 WebSearch で最新確認）

- 日本:
  - Kyash（バーチャル + 上限設定）
  - B/43（プリペイド + ポット機能）
  - 三井住友 Olive のフレキシブルペイ
  - 楽天プレミアムカードの家族カード別枠運用

- 海外・法人:
  - Revolut（使い捨てバーチャル）
  - Stripe Issuing（法人向け発行API）
  - Brex / Ramp（法人）

#### 必須の上限設定

- 月額利用上限: 想定額の1.5倍程度
- 1回利用上限: AI API なら1万円単位
- 海外利用: 不要なら OFF
- コンタクトレス / ECのみ: カテゴリ別制御
- 通知: 利用都度のプッシュ / メール通知を ON

### 3. APIキー・認証情報の分離

#### 提案する構成

```
用途別に複数発行:

Claude API
  ├─ production-key（厳しい上限・本番アプリ）
  ├─ development-key（中上限・開発）
  └─ experiment-key（最小上限・お試し）

OpenAI API（同様）
AWS / GCP（IAM で用途別ロール）
Stripe（restricted key を用途別に）
GitHub（fine-grained PAT を用途別に）
```

#### 管理場所

- パスワードマネージャー: 1Password / Bitwarden / Apple Keychain / Google Password Manager
- OSキーチェーン: macOS Keychain / Windows Credential Manager
- 環境変数（`.env`）: 必ず `.gitignore` + ローカルのみ
- シークレットマネージャー: AWS Secrets Manager / GCP Secret Manager / HashiCorp Vault / Doppler / 1Password Secrets Automation

#### 絶対にやらないこと

- Gitリポジトリに平文でコミット（事故の最頻出源）
- Slack / Discord / メール で送る
- スクリーンショットに写り込ませる
- CLAUDE.md / SKILL.md / 設定ファイルに直接書く

#### ローテーション

- 最低でも四半期に1回 キー再発行
- 漏洩疑義があれば即日
- 退職・外注解除時 に即日
- ローテーションできない設計なら、そもそも使わない

---

### 4. 実行環境のサンドボックス化

#### レベル1（最小限）

- 別ユーザーアカウント: OSの別ユーザーで AI を動かす
- 別ディレクトリ: 重要データと作業ディレクトリを分ける
- `.gitignore` 厳格化

#### レベル2（Docker）

- Docker コンテナで AI 実行環境を隔離
- ファイルマウントは最小限に
- ネットワーク制限（必要な外向き通信だけ許可）

#### レベル3（完全分離）

- 専用 VM / 別物理マシン
- クラウドの専用アカウント（AWS/GCP/Azure の別アカウント）
- VPN / ネットワーク分離

---

### 5. 家・インフラ側

- Wi-Fi の管理者パスワード変更（初期パスワードのまま使わない）
- ルーターのファームウェア更新
- IoT機器（スマートスピーカー等）の分離ネットワーク
- 端末ロック（スクリーンロック + 長めのパスコード）
- MFA 全面化（SMS より TOTP / Passkey 推奨）

## 設計ワークフロー

### ステップ1: 棚卸し（Current State）

ユーザーと一緒に「今どうなっているか」を洗い出す:

```markdown
## 現状棚卸し

### 金融
- メイン銀行: ___
- サブ口座: あり / なし
- AI課金カード: メインと同じ / 別
- 月額サブスク合計: ¥___

### 認証情報
- パスワードマネージャー: 使用中 / 未使用 / ___
- APIキー数: 約___本
- MFA適用率: 全部 / 一部 / 未適用
- .envをGitコミットしたことがある: はい / いいえ

### 環境
- AI実行: ホスト直 / Docker / VM / その他
- 端末ロック: あり / なし
- Wi-Fi管理者パスワード変更: したことある / ない

### AI設定
- CLAUDE.md: 自分で管理 / 理解していない
- hooks: 使用中 / 未使用 / 不明
- MCP数: ___個
```

### ステップ2: リスク評価（Threat Model）

各要素について「漏れたら何が起きる？」を具体化:

```markdown
## リスク評価

| 要素 | 漏れたときの被害 | 現在の対策 | 推奨 |
|------|----------------|----------|------|
| メインカード | 全生活の金銭被害 | なし | AI用と分ける |
| Claude API key | API quota 消費 + 情報アクセス | 上限未設定 | 用途別分割 + 上限 |
| GitHub PAT | プライベートリポジトリ流出 | classic PAT | fine-grained PAT + 期限 |
| ...
```

### ステップ3: 設計ロードマップ（Roadmap）

優先度を付けた実行計画を出す:

```markdown
## 今日やる（1時間以内）
- [ ] Kyash / B/43 でAI専用バーチャルカード発行
- [ ] 1Password 導入 + 既存パスワードインポート

## 今週やる（数時間）
- [ ] サブ銀行口座 開設手続き
- [ ] Claude API key を 3本に分割
- [ ] MFA 全面化

## 今月やる
- [ ] Docker 環境整備
- [ ] 週次 patrol スケジュール
- [ ] 月次 audit スケジュール

## 継続
- [ ] 四半期キーローテーション
- [ ] 年次 全面見直し
```

### ステップ4: 入口チェックリスト発行

次の「導入ゲート」モードで使えるチェックリストをプロファイルに記録:

```yaml
intake_ready:
  dedicated_card: true       # AI専用カード用意済み
  dedicated_bank: true       # AI専用口座用意済み
  password_manager: true     # パスマネ使用中
  mfa_coverage: full         # MFA全面化済み
  api_key_separation: true   # APIキー用途別
  sandbox_available: docker  # Docker 使用可能
  patrol_scheduled: weekly   # 週次巡回済み
  audit_scheduled: monthly   # 月次監査済み
```

これらが 揃ってから 新ツールの導入を許可する（intake-gate モードで参照）。

## advocate との連携

設計が一通りできたら 必ず security-guard-advocate を起動し、

- 「この設計の穴」
- 「攻撃者がどう突くか」
- 「サプライチェーン攻撃の入口」
- 「ユーザー自身が最弱リンクになる点」

を批判的にレビューしてもらう。

## やらないこと

- 「これで絶対安全」と断言する（必ず残存リスクを列挙）
- ユーザーの現状を軽視した過剰な設計（実行可能なレベルから）
- 認証情報の預かり（絶対）
- 他人の環境・他社システムの設計（本人・自社の明示許可のみ）
