# 機能: 導入ゲート（Intake Gate）

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.security-guard/config.yaml` と
> `./.security-guard/zero-trust-profile.md` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` は config.yaml の値を、
> 「プロファイル（intake-design で作ったもの）」は zero-trust-profile.md の蓄積内容（`intake_ready` 等の整備状況含む）を指す。
> プロファイル未作成なら「intake-design 未実施。判定の前提が揃わないため、まず intake-design を推奨」と明示してから進めること。


新しい MCP / SaaS / AIツール / ライブラリを使い始める前に、入口と出口が整っているかを判定する機能。整っていなければ導入を止める。

## なぜ導入ゲートが必要か

どれだけ注意深くツールを選んでも、以下は避けられない:

- 導入したMCPが実は過剰な権限を要求していた
- 使い始めた後で脆弱性が発表された
- 無料プランのつもりが自動課金されていた
- ログを残さない設計で、後から何にアクセスされたか分からない
- 試しに入れたまま忘れて数か月放置していた

これらは、導入する「前」に止めるのが一番確実です。
「入れてから考える」ではなく、「整ってから入れる」を徹底するのが、ゼロトラスト運用の肝です。

## 判定ワークフロー

### ステップ1: 対象の確認

ユーザーに以下を聞く:

```
導入したいツールについて教えてください:

1. ツール名・種類（MCP / SaaS / AI / ライブラリ / ブラウザ拡張 等）
2. 何に使う予定？
3. 公式URL / リポジトリURL
4. 課金形態（無料 / 月額 / 従量）
5. 代わりになる既存ツールで済む可能性はある？
```

### ステップ2: 最新情報を調査

その時点の評判・脆弱性・公式ポリシーを必ず WebSearch で確認:

```
{ツール名} security issue {今年}
{ツール名} data retention policy
{ツール名} permissions scope
{ツール名} known vulnerabilities
{ツール名} vs alternatives
```

特に MCP の場合は:

```
{MCP名} github issues security
{MCP名} supply chain
{MCP名} 公式 or 非公式
```

### ステップ3: 入口チェック

以下8項目を確認。プロファイル（intake-design で作ったもの）と照合:

| 項目 | 要件 | 合否 |
|------|------|------|
| 1. 専用アカウント | 既存メインアカウントと分離できるか | ⬜️ |
| 2. 専用決済 | AI専用カード / 少額決済で払えるか | ⬜️ |
| 3. 最小権限認証 | 必要な権限だけ持つAPIキー・OAuthで接続できるか | ⬜️ |
| 4. ローテーション可能 | キー・トークンを後で差し替えできるか | ⬜️ |
| 5. 上限設定 | 利用量・金額の上限を設定できるか | ⬜️ |
| 6. サンドボックス | 別環境（Docker / 仮想環境）で動かせるか | ⬜️ |
| 7. 公式供給元 | 公式 or 信頼OSS か（野良MCPは警戒） | ⬜️ |
| 8. 脆弱性情報 | 直近90日で重大な脆弱性報告がないか | ⬜️ |

### ステップ4: 出口チェック

| 項目 | 要件 | 合否 |
|------|------|------|
| 1. ログ | 操作ログ・アクセスログが残るか | ⬜️ |
| 2. アラート | 異常利用時に通知が飛ぶか | ⬜️ |
| 3. 監視対象 | patrol / audit の定期監視対象に含められるか | ⬜️ |
| 4. 撤退容易性 | やめたい時に即時停止・完全削除できるか | ⬜️ |
| 5. データエクスポート | 作ったデータを取り出せるか（ベンダーロックイン対策） | ⬜️ |

### ステップ5: 判定

以下のいずれかで明示:

- 合格（導入可）: 入口・出口どちらも揃っている
- 条件付き合格: いくつか未整備だが、対策を添えて使うなら可
- 不合格（再評価）: 整備してから再度判定

### ステップ6: 合格しない場合の整備リスト

不合格項目を具体的な行動に落とす:

```markdown
# {ツール名} 導入判定: 条件付き合格

## 不足している項目
1. 専用カード未整備 → 先に Kyash でAI用バーチャルカード作成
2. 上限設定不明 → 公式ドキュメントを確認、設定可能なら上限 ¥10,000/月
3. ログ機能不明 → サポートに問い合わせ、不可なら導入見送り

## 整備後の再判定
1〜3を整えたら再度 intake-gate で判定。
```

## 出力フォーマット例

```markdown
# 導入ゲート判定: Cursor (開発エディタ)

## 対象
- 名前: Cursor
- 種類: AI支援エディタ (SaaS)
- 用途: コーディング時のAI補助
- URL: https://cursor.com
- 課金: 個人Pro 月$20

## 最新情報調査（{YYYY-MM-DD}時点）
- 脆弱性: 直近90日で重大な報告なし
- データ保持: Pro プランは学習に使われない設定可
- 権限: ローカルファイル・エディタコンテキスト送信
- 代替: GitHub Copilot / Continue 等

## 入口チェック
| # | 項目 | 判定 | メモ |
|---|------|------|------|
| 1 | 専用アカウント | 合 | 別Googleアカウントで登録 |
| 2 | 専用決済 | 合 | AI用Kyashカード登録 |
| 3 | 最小権限 | 合 | 機密ディレクトリは `.cursorignore` で除外 |
| 4 | ローテーション | 部分合 | サブスクは毎月更新、アカウント削除は即時可 |
| 5 | 上限設定 | 合 | 月定額で上限明確 |
| 6 | サンドボックス | 条件付き | 本番コードで使う場合は別プロジェクトに分離推奨 |
| 7 | 供給元 | 合 | Anysphere 公式 |
| 8 | 脆弱性 | 合 | 重大報告なし |

## 出口チェック
| # | 項目 | 判定 | メモ |
|---|------|------|------|
| 1 | ログ | 合 | 管理コンソールから利用履歴確認可 |
| 2 | アラート | 部分合 | サブスク上限は明確だが、異常利用通知はなし |
| 3 | 監視対象 | 合 | audit モードで `.cursorignore` を定期確認 |
| 4 | 撤退 | 合 | サブスク解約で即停止 |
| 5 | エクスポート | 合 | コードは手元、設定はJSONエクスポート可 |

## 判定
条件付き合格

## 条件
1. 機密ディレクトリを `.cursorignore` で除外
2. 本番リポジトリではなく開発ブランチで利用
3. 月次 audit で設定変更を確認
4. 1年以内にデータ保持ポリシーを再確認
```

## 特に警戒するケース

### 野良MCP

- GitHub スター数が極端に少ない
- 作者情報が不明瞭
- npm / PyPI に突然現れた新規パッケージ
- 公式と紛らわしい名前（例: `anthropic-mcp-helper` を装う非公式パッケージ）

→ 安易に入れない。公式・有名OSS・信頼できる開発者のもの以外は避ける。

### 「無料なのに高機能」

- 「なぜ無料で提供できるのか」を考える
- データを学習利用する / 広告表示する / 有料版誘導 のどれかが多い
- それを許容できるかで判断

### エージェント連鎖

- MCP A が MCP B を呼び出す、さらに B が外部APIを呼ぶ
- チェーンが長くなるほど監査が困難になる
- 原則: チェーンは短く。1段で終わるように設計する

## advocate との連携

判定が難しい場合、security-guard-advocate に以下の観点でレビューを依頼:

- 「この判定は楽観的すぎないか？」
- 「攻撃者がこのツールを足場にできないか？」
- 「1年後に問題が顕在化するシナリオは？」

## 絶対にやらないこと

- 「有名だから安全」で判定する（脆弱性は有名ツールにも出る）
- 入口チェックだけで出口チェックを省く
- 過去の判定をそのまま使う（ツールも環境も変わる）
- ユーザーが急いでいるからと判定を甘くする
