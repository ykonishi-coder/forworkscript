# 機能: エスカレーション判定

> 前提: 呼び出し元（SKILL.md）の「設定の読み込み」で `./.customer-support-advisor/config.yaml` を読み込み済み。
> 未読込なら先に読むこと。本ファイル内の `config.xxx` はその値を指す。


問い合わせ内容を読んで、担当者の通常対応で完結させていいか、上位担当者・専門部署・責任者へ引き継ぐべきかを判別する。

## 「エスカレーション」って何？（初心者向け）

カスタマーサポートの世界で「エスカレ」と呼ばれるのは、現場担当者では判断しきれない問い合わせを、上司・専門部署・責任者など上位に引き継ぐことです。

上位へ引き継ぐべきかどうかの判断を間違えると:
- 引き継ぎすぎ → 上位の時間を消費して現場が機能しない
- 引き継がなさすぎ → 本来対応すべき人が気づかず、顧客離れ・大事故に発展

この判別を基準化して、現場担当者が迷わず運用できるようにするのがこの機能です。

---

## 判定の3軸

### 1. 緊急度
- サービス停止・障害中？
- 顧客の業務・契約期限に直接影響する？
- 法令・金融・医療など外部期限が絡む？

### 2. 感情度
- 怒り・悲しみ・失望・強い不満が読み取れる？
- 「解約する」「訴える」「SNSに書く」など強い表明がある？
- 繰り返し問い合わせてきて、一向に解決していない？

### 3. 金額・影響範囲
- 対応を誤ると金銭的損害が発生する規模？
- 複数顧客に影響する恐れ（プラン変更・データ破損）？
- 契約に関わる判断（解約・料金変更・特別対応）？

---

## 判定レベル

| レベル | 条件 | 対応 |
|-------|------|------|
| L0: 現場完結 | 3軸いずれも低 / FAQで答えられる | テンプレ回答で完結 |
| L1: 担当者+テンプレ | 軽微な苦情や通常の質問 | 担当者が個別回答、テンプレ活用 |
| L2: 上司確認 | 感情度中〜高 or 金額影響中 | 返信前に上司チェック |
| L3: 専門部署・責任者 | 法務・技術・経営判断が必要 | 専門部署へ引継ぎ、責任者名で返信 |
| L4: 緊急・重大 | サービス停止・重大クレーム・法的リスク | 即座に責任者・関係者集約、迅速初動 |

---

## 判定フロー

ユーザーから問い合わせ文を受け取ったら以下を順に評価:

```
1. 明らかに L4（即緊急）のサイン?
   - 「障害発生」「サービス使えない」「SNSで拡散します」
   - 法的・金銭的な脅威を含む表明
   - 複数顧客からの同時報告
   → YES なら L4 で即時レポート

2. 感情度は? (低 / 中 / 高)
   - 文面のトーン、繰り返し回数、ワード選び
   - 「怒っています」「本当にがっかり」「ひどい」等の直接表現

3. 緊急度は? (低 / 中 / 高)
   - 期限・タイミングが絡むか
   - 業務停止・決済失敗・契約関連か

4. 金額・影響範囲は? (低 / 中 / 高)
   - 返金規模、複数顧客影響、契約変更要求

5. 3軸をスコア化してレベル判定
   - 高が1つ以上 → L3以上を検討
   - 中が2つ以上 → L2以上を検討
   - すべて低 → L0〜L1
```

## 判定の出力フォーマット

```markdown
## エスカレーション判定結果

### 問い合わせ要約
（受領した問い合わせの要旨を2〜3行で）

### 3軸評価
- 緊急度: 低 / 中 / 高 （根拠）
- 感情度: 低 / 中 / 高 （根拠）
- 金額・影響範囲: 低 / 中 / 高 （根拠）

### 判定レベル
L{n}（タイトル）

### 推奨アクション
1. 次に動くべき人: {担当者 / 上司 / 専門部署 / 責任者}
2. 初動期限目安: {◯時間以内 / 翌営業日 など}
3. 返信トーン: {共感優先 / 事実説明優先 / 法務確認待ち等}
4. 返信ドラフト: （担当者が送る前提の原案）

### 注意点
- 取るべき証跡（スクショ・ログ・前後のやり取り）
- 触れてはいけない話題（係争中の金額など）
```

## エスカレ基準の「組織別カスタマイズ」

業種・規模で基準は変わる:

### 例: EC・D2C
- 「商品が届かない」→ 配送段階で L1 / 未着2日超えで L2
- 「不良品」→ 写真有無で L1 / L2
- 「返金」→ 金額5,000円未満 L1 / 以上 L2

### 例: SaaS
- 「ログインできない」→ 個別 L1 / 複数報告で L3 緊急
- 「データが消えた」→ 即 L3 以上（バックアップ確認）
- 「値上げ反対」→ L2 で上司判断

### 例: 医療・金融
- 重要性高いため、平均より一段上のレベルで運用推奨

ユーザーの業種・規模を確認し、基準値を調整。`templates/escalation-criteria.template.md` にカスタム基準を保存。

---

## 運用のコツ

### 判定履歴を残す
- 全判定結果をローカルに保存
- 後日レビューして基準をアップデート
- 「L1判定が実は L3 案件だった」事例を学ぶ

### 現場の裁量も残す
- AI判定は参考。最終判断は必ず人間
- 「AIが L1 と言ったから放置」は絶対にダメ

### 判定の偏りチェック
- すべての問い合わせが L0〜L1 ばかり → 基準が甘い可能性
- 半数以上が L3 以上 → 基準が厳しすぎ or 根本的な製品課題あり

## advocate との連携

判定結果を customer-support-advisor-advocate に渡して:

- 「この判定は顧客視点で妥当？」
- 「実はもっと高いレベルではないか」
- 「感情度を過小評価していないか」

を批判的にレビューしてもらう。

## 絶対にやらないこと

- AI判定だけで返信送信・返金処理など実行
- 個人情報（メール本文含む氏名・連絡先）を外部に送信
- 判定基準を一度作ったきり更新しない
- 「L0」と判定したら読み返さず放置する運用
- 顧客の感情表明を「過剰」「モンスター」とラベル付けして軽視する
